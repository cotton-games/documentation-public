## Usage et fichiers à déployer

Déployer uniquement `games/web/test_bots.php` et `games/web/includes/bots/hub_bots.js`. Aucun changement de serveur WS, aucun restart requis pour ce lot. Recharger la page `/test_bots.php` du même environnement que le Hub.

Coller le token sélectionne automatiquement « Hub (Quiz, Blind Test, Bingo) » et masque le champ session ; aucun ID de session n’est requis. On peut aussi choisir ce mode puis coller le token ou l’URL `/hub/{token}/master` (ou `/play`), choisir 1 à 200 bots et lancer. Le token est extrait, mais les appels restent sur l’origine courante ; l’URL collée ne sert jamais de destination réseau. La session n’a pas besoin d’être lancée. Les bots s’inscrivent au Hub puis attendent le focus numérique joignable. Conserver la page ouverte.

Avant admission, `current_player` permet de reprendre une identité encore active sans nouvelle inscription. Une identité `left` est remplacée par une nouvelle clé et un nom `HubBot-NNN-xxxxxx` (moins de 20 caractères), persistés avant HTTP. Les conflits `USERNAME_TAKEN`/`USERNAME_REFERENCED` autorisent au maximum trois tentatives avec renouvellement ; les refus de jauge et autres erreurs ne déclenchent pas ce renouvellement. Aucune règle publique Global n’est modifiée.

Les identités aléatoires `p:<uuid>` sont conservées dans localStorage par Hub et par index. Relancer le même effectif dans le même navigateur reprend les identités ; augmenter l’effectif ajoute des candidats. Le compteur de jauge est celui renvoyé par le Hub, les refus sont affichés. Aucun fallback de quota ni endpoint d’admission dédié.

« Arrêter les bots » arrête le suivi et envoie le départ volontaire de session (`quitGame` Quiz/BT, `player_quit` Bingo), tout en conservant les places Hub. Le changement automatique de focus reste une simple déconnexion. « Faire quitter le Hub aux bots » utilise `leave_player` pour les bots admis du lancement courant. Avant de réduire l’effectif ou de changer de Hub, faire quitter les bots si les places doivent être libérées ; la fermeture de page conserve aussi les inscriptions. Après départ, le contrat public réserve le nom historique : une nouvelle inscription utilise une nouvelle clé et un nom suffixé, soumis à la jauge. Les anciens résultats restent attachés à l’ancienne identité.

## Contrat technique

Actions publiques existantes de `/hub/{token}/play` : `current_player`, `register_guest`, `active_launched_session`, `leave_player`. Requêtes sans cookies (`credentials: omit`) : chaque bot fournit son propre `player_token`, sans utiliser ni remplacer l’identité du navigateur. Timeout HTTP Hub 15 s. Admissions séquentielles ; suivi séquentiel puis pause 5 s, pas de rafale de polls parallèle. Les profils runtime proviennent de `access` validé par le Hub ; aucun accès forcé si attente, papier, fin ou absence de `should_redirect_to_play`.

Quiz/Blind Test : réutilisation de la participation matérialisée par l’accès Hub, puis garde WS existant. Bingo : même clé Hub transmise au player_register idempotent et attribution/hydratation de grille existantes, puis garde WS. Pas de bot numérique lancé en papier. Identité Hub conservée entre les jeux. Le changement de focus coupe les anciens sockets avec code navigateur 4010, sans `quitGame`, `player_quit` ni désactivation destructive ; il ne libère pas une place Hub.

Simulation dans le navigateur, pas de nouveau service bots serveur. Les contrôles de niveau et les moteurs de réponses/coches existants sont conservés. Mode session historique préservé. Ne pas utiliser simultanément plusieurs onglets sur le même roster local (les connexions d’une même identité se remplacent).
